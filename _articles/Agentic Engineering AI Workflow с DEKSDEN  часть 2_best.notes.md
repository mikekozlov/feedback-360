## Тезис
Полный цикл разработки ПО не изменился (хотелка → спецификация → план → код → верификация → деплой) — изменился инструмент: теперь каждую стадию ведут агенты. Чтобы агент давал предсказуемый результат, его на каждом шаге нужно кормить **эффективным контекстом** из структурированного файлового **Memory Bank** и замыкать **детерминированным приёмочным сценарием** — без цикла обратной связи модель не способна сама убедиться, что хотелка реализована.

## Контекст
Вторая встреча Ведущего с Денисом на канале «AI-Driven Development»; формат — практический разбор личного workflow гостя «по этапам», от формулировки требований до QA и деплоя. Денис прошёл большой путь автоматизации, набил много «шишек» и не стесняется делиться. Разговор идёт на фоне свежих релизов GPT-5.x и «холивара» Codex vs Claude Code.

## 1. Общая идея: цикл разработки не изменился, изменился исполнитель

Денис формулирует рамку всей встречи: классический жизненный цикл разработки (хотелки → спецификации → план → реализация кода → верификация → деплой) остался прежним, но теперь на каждой стадии работает агент, а не только на этапе написания кода. Денис довёл несколько практических кейсов до состояния, когда **весь цикл** реализован агентами, а не только генерация кода.

**Конкретика:** стадии — бриф (оформление хотелки) → спецификация → план → код → верификация → деплой. Модели на момент записи: работали на GPT-5.2 «на high», затем перешли на 5.4; обсуждают, что «high» зачастую оптимальнее, чем «extra high», а 5.4 умеет запускать субагентов и комментировать ход работы, но «жадно» и быстро набирает контекст.

**Цепочка рассуждения:**
1. Святой Грааль — кнопка «сделай всё хорошо» — пока не просматривается.
2. Парадокс: автоматизация не уменьшает объём работы, а позволяет (и провоцирует) делать больше.
3. Смысл — смещать работу от рутины к творчеству и реализации идей, рутину («прописывание деталей») отдавать агентам.

**Что это даёт:** установка на то, что ценность человека — в постановке задачи и проверке результата, а не в ручном кодировании.

## 2. От «хотелки» к спецификации: снять неопределённость до кода

Первый мост цикла — превратить произвольно сформулированную «хотелку» в спецификацию. Денис делает это в два приёма: (1) «отстроить по габаритам» — обозначить зону изменений и масштаб (новая фича / доработка существующей), (2) внутри хотелки снять все противоречия. Ключевой ход — заставить агента переформулировать задачу своими словами, заполнить недосказанности и **задать уточняющие вопросы** (во многих агентах функция вопроса ещё и предлагает готовые варианты ответа — часто достаточно их зафиксировать).

**Конкретика:** Plan Mode появился у Claude Code, Gemini, Codex и других агентов (ещё пара названий в исходнике осталась нерасшифрованной). Пример сквозной задачи у обоих собеседников — «система рекомендаций в интернет-магазине».

**Пример:** недостаточно сказать «хочу систему рекомендаций» — нужно задать, для каких клиентов, какие товары включены, нужны ли нишевые сегменты; должна ли она выдавать список товаров, подсказывать категории или показывать «эфемерный товар» в корзине для добавления одним кликом.

**Цепочка рассуждения:**
1. Если агенту не сказать деталь — он её выдумает (галлюцинация — это норма, не баг).
2. Мы используем ИИ именно за то, что он «придумывает», но здесь нам нужен наш результат, а не его.
3. Значит, неопределённость надо снять явным диалогом до начала планирования.

> [Денис]: не надо воспринимать это галлюцинации как какой-то баг или недостаток. Это, собственно, то, ради чего мы искусственный интеллект юзаем.

**Что это даёт:** спецификация перестаёт опираться на догадки модели; дальше можно планировать реализацию.

## 3. Memory Bank: контекстный движок проекта

Хотелка реализуется не в вакууме, а внутри существующей системы, поэтому её нужно **граундить** (привязывать) к проекту. Для этого Денис ведёт **Memory Bank** — структурированную информацию о проекте, из которой агент извлекает, какие зоны проект затрагивает и что нужно изменить. Главный приём навигации — **индексные файлы** с *аннотированными ссылками*: на каждую ссылку два блока — «что лежит» и (важнее) «зачем это читать».

**Конкретика:** даже современные модели (контекст которыми хвалится OpenAI) на проектах «чуть больше маленьких» без Memory Bank выдают дублирующийся код, который «расползается» — всё, что выходит за эффективный контекст модели, теряет связность. Главные индексные файлы Денис делает по образцу `CLAUDE.md` / `AGENTS.md` («стандартный файл агента»).

**Цепочка рассуждения:**
1. Никакая информация не нужна агенту в 100% случаев → индекс маршрутизирует его к нужному.
2. Если в индексе писать только «что» (скупо), агент не понимает, как это соотносится с задачей, и не открывает файл.
3. Если добавить «зачем» — шанс, что агент прочитает файл в нужный момент, резко растёт.

> [Денис]: MemoryBank это вспомогательный инструмент для формирования контекста агента

**Пример (антипример из инфополя):** «скандальный документ», где якобы `AGENTS.md` мешал работе и без него результаты были лучше. По Денису, это «фейковое исследование»: туда заливали мусор в контекст и путали агента — то есть проблема в неудачных формулировках индексных файлов, а не в самой идее.

**Что это даёт:** агент сам добирает только нужные «кусочки» контекста (см. Progressive Disclosure в глоссарии).

## 4. Структура Memory Bank: спеки, Epic/Feature, домен, трассировка

Memory Bank у Дениса разбит по видам документов. Спецификации описывают, **как система сделана сейчас** (по модели C4, level 1: что за продукт, для кого, каким стеком реализован, что в MVP/не в MVP, архитектурные подходы, вертикальные слайсы, структура файлов). Отдельно — папка планов, нарезанная как **Epic и Feature** вокруг ценности для пользователя (Epic ≈ roadmap со статусом во FrontMatter; Feature — минимальная единица delivery). Плюс доменный срез (доменная специфика проекта). Ведущий формализует: Memory Bank ≈ документация для агента + таск-трекер + база знаний.

**Конкретика:** учебный проект **Feedback 360 / HR 360** (система оценки 360°), сделан «за пару дней» с нуля специально для разбора; принципы ведения лежат в папке **MBB** (Memory Bank Bible). Пример доменного правила: **политика анонимности** — если от группы респондентов получено меньше двух оценок, группа не показывается (чтобы не «спалить» анонимность ответивших).

**Цепочка рассуждения (зачем трассировка «намерение → реализация»):**
1. Каждый файл кода связан с конкретной фичей, а не «болтается».
2. Модель может «сгонять» к описанию фичи и понять, для чего пользователь её использует.
3. Для ответственного софта (платёжные системы, медицина) сквозная трассировка вообще требование стандарта.

**Что это даёт:** агент понимает не только «как», но и «зачем» написан код; планирование = граундинг фичи на текущее состояние системы.

## 5. Пирамида знаний и борьба с дрифтом документации

Главный риск базы знаний — рассинхрон (дрифт) с кодом, при котором код перестаёт быть Single Source of Truth. Решение Дениса — **жёсткий Single Source of Truth** плюс **пирамида знаний**: в коде содержится то, *как* сделано, а в документации — *почему* и *для чего*. Сигнатуры и детали в документацию не дублируются: агенту несложно сходить в код и посмотреть. Детерминированного правила «это только в код, это только в документацию» Денис так и не нашёл — граница оценочная, её решает агент.

**Конкретика:** пример «близкого к коду» в документации — `results.getHRView` — оказался идентификатором экрана (отдельная подсистема идентификаторов), а не утечкой сигнатуры.

> [Денис]: Это когда мы в коде содержим то, как это сделано, а выше в документации мы пишем, почему это сделано и для чего это сделано.

**Цепочка рассуждения:**
1. Дублирование «код + та же информация в доке» забивает контекст.
2. При изменениях агент не всегда синхронно правит и код, и доку → они «разъезжаются» → глюки.
3. Значит, дублирования надо избегать в принципе, а не «синхронизировать».

**Что это даёт:** меньше дрифта и меньше расхода контекста; принцип важнее жёсткого правила.

## 6. Приёмочный сценарий и цикл обратной связи

Денис в каждую спецификацию/хотелку теперь обязательно встраивает **обратную связь** — доказательство того, что фича реализована. Для каждой фичи проговаривается **тестовый/приёмочный сценарий** (на верхнем уровне похож на интеграционный тест, прогоняемый от имени пользователя, возможно кросс-эпиковый). Это не «тесты ради тестов»: без цикла обратной связи агент не способен сам убедиться в результате.

**Конкретика:** под сценарий нужны подготовленная БД и **seed** (пример: интернет-магазин с лодкой, мотором, вёслами в таблице товаров — предопределённый набор данных под ожидаемый результат). Аналогия: «представьте, что фичу заказали вам как аутсорсеру — по какому сценарию вы сдаёте её заказчику».

**Цепочка рассуждения (почему агенту это критично):**
1. Современные модели продумывают на 1–2 уровня абстракции, дальше «латентное пространство не сворачивается».
2. Умозрительно, просто читая хотелку, агент не может понять, реализована она или нет — нужен чёткий критерий.
3. Увидев расхождение с критерием, агент способен «добить разницу» — но только если критерий есть.

> [Денис]: это фундаментальное ограничение модели, она не может спрогнозировать, как ваш код сработает в системе, она может только с некоторой вероятностью ожидать этого.

> [Денис]: Это некий интеграционный тест, который если прошел, значит фича реализована.

**Что это даёт:** без приёмочного теста хотелку «проверить невозможно», и высока вероятность, что она реализована не так, как обсуждалось. (Ведущий отмечает смежный тренд: Full-Stack Developer теперь включает и тестирование, и продуктовую сторону.)

## 7. Промпты, скиллы и reverse-engineering open source

Денис ведёт коллекцию переиспользуемых промптов в **Obsidian** (а не внутри агента), потому что периодически работает с разными агентами (Codex, Claude Code, OpenCode), а промпты у них лежат в разных папках. Простой промпт «прочитай MBB и расскажи, что понял» «не стоит скилла». Ведущий даёт лайфхак: скачать учебный проект, натравить агента на папку Memory Bank и попросить сгенерировать **обобщённый (generalized) скилл** — это «реверс-инжиниринг» готового результата в промпт/скилл.

**Конкретика:** существует официальный **skill-creator**; Денис сделал свой **скилл-ревьюер**, который по лучшим практикам (в т.ч. «по книжке от Anthropic») аудирует и улучшает скиллы, и отправил его в Anthropic на публикацию. Отдельный приём — извлекать функциональность из open-source: Денис так достал из открытого проекта логику работы с несколькими аккаунтами для оркестратора (переключение при исчерпании лимита). Его минималистичный скилл **Codalive «на минималках»** запускает отдельный экземпляр Claude Code с моделью **Haiku**, чтобы дёшево собрать нужное по репозиторию; работает и из Codex, и из Claude.

**Цепочка рассуждения:**
1. У нас уже есть готовый результат (структура проекта) — значит, промпт можно вывести из него, а не писать с нуля.
2. Технология «возможна с 2025 года» (поправка в кадре: «мы в 26-м году») и проста за счёт open source.
3. Для больших репозиториев — полноценный Codalive.

**Что это даёт:** быстрый способ обобщать собственный workflow в переиспользуемые скиллы.

## 8. Язык, токены, таск-трекеры и Swarm

По языку: русский даёт примерно **+20–30%** токенов (звучали и более резкие оценки — «чуть ли не x2», «до 50»), **но** в протоколе работы кодингового агента промпт идёт на русском, а думает и читает код агент на английском — итоговый контекст «процентов на 90» английский. Поэтому реальная экономия на языке сводится к ~0,5–1% контекста, и «любой личный запрос к модели убьёт всю экономию». Денис всё равно пишет на русском: быстрее читать (а читать приходится много) и лучше формулировать; подготовительный этап (парное обдумывание, брейншторм) на родном языке снижает когнитивную нагрузку.

По хранению: Memory Bank — это файлы, и для агента это удобнее классических таск-трекеров. Агент **lazy**-лезет либо в файловую систему, либо в MCP; откуда забирать задачу (Linear, Jira, Memory Bank) — не так важно, важно — куда и как **структурировать**.

**Конкретика:** у OpenAI есть оркестратор **Swarm**, который выкачивает задачки из **Linear** и даже отчитывается. Денис тестировал Swarm: информацию собирает и следует инструкциям хорошо, но **меняет данные плохо** — центральный агент инструктирует субагентов слишком лаконично; Swarm сжигает «невообразимое количество токенов» и пока «эксперименты».

**Цепочка рассуждения (почему файлы > таск-трекеры для агента):**
1. В файл агент пишет что захотел и когда захотел; таск-трекер требует определённую структуру данных.
2. Внешние системы спроектированы для людей; их структура задаётся не вами, а системой.
3. Главное — они могут не поддерживать **Progressive Disclosure** (добор контекста кусочками), и агент вынужден выкачивать кучу информации, забивая контекст и «расфокусируя внимание».

**Что это даёт:** для агентной части проекта Денис ведёт знания в файлах; корпоративные инструменты — «либо дождутся адаптации под агента, либо костыли синхронизации».

## 9. QA: SDK→CLI→GUI, Page Object Model и стабильные идентификаторы

Подход Дениса к интерфейсам: клиентскую логику инкапсулировать в **SDK**, поверх него повесить простой для агента **текстовый интерфейс / CLI**, гонять логику через CLI, и только когда отлажено — строить графику. Каждый интерфейс описывается **структурно** (не «рамочки и скругления», а: как система разбита на экраны, какая информация на каком экране, какие действия откуда возможны). Каждому экрану и каждому структурному элементу — **стабильный уникальный идентификатор**.

**Конкретика:** в вебе идентификаторы уходят в атрибут **`data-testid`**, который умеют использовать Playwright или Chrome CDP; в текстовом интерфейсе — просто стабильный id, связанный с кнопкой. Обёртки экранов — **Page Object Model** (изначально браузерная вещь, но решение универсальное: объект = API к экрану, через который строятся сценарии).

**Цепочка рассуждения:**
1. Тестировать через распознавание скриншотов — медленно и ненадёжно.
2. Без стабильных идентификаторов селекторы Playwright «не всегда надёжно срабатывают» → «пляшущие» тесты.
3. Стабильные id → сценарии «бегают надёжно».

**Что это даёт:** детерминированное место даже для сложного интерфейса.

## 10. AI-QA против детерминированных тестов; вертикальные слайсы

Ведущий вводит различение: **manual AI QA** (агент сам открывает страницу, находит идентификатор, кликает) против классических **N2N / end-to-end** тестов. AI-QA менее повторяем: «может найти проблему, а может не найти», от раза к разу ведёт себя по-разному → меньше доверия. Денис согласен и формулирует жёстко: если агент во время прогона браузера случайно наткнулся на ошибку — это **провал тест-системы**, детерминированные тесты должны были её поймать. Цель — замкнуть «колесико»: хотелка → спецификация → фича → **детерминированный приёмочный тест**.

**Конкретика:** по оценке Ведущего, **99% кейсов** покрываются стандартными end-to-end тестами; в крайнем случае — E2E с записью видео, которое потом анализирует агент. Отдельный плюс — **вертикальные слайсы**: зона изменений локализована, тестировать нужно меньше подсистем; на малом объёме (2 объекта против 50) агент лучше продумывает граничные/edge-кейсы (пустые/длинные данные, спецсимволы, нарушающие бизнес-правила).

> [Денис]: Я считаю, что это fail-тест системы.

> [Ведущий]: Нужно больше спать.

**Что это даёт:** ставка на повторяемость и быстрый фидбэк (медленнее юнитов/интеграционных, но быстрее «гуляющего» агента).

## 11. Инструменты тестирования и закат «толстого» MCP

Браузерных инструментов «по большому счёту два с половиной»: **Playwright** и **Chrome CDP** (CDP жёстко привязан к Chrome). Отдельно отмечен инструмент, экспозящий одну функцию «выполнить код», внутри которой агент сам пишет на **Playwright API** цепочку действий (автор — некий «Виталианис»; ещё пара названий инструментов в исходнике осталась неразборчивой). Большой сдвиг — от **MCP** к связке **Skill + CLI**: Денис сконвертировал почти все свои MCP в CLI-обвязки через **MCPorter** (автор — «Питер») и MCP «давно не использует».

**Конкретика:** скилл легко заюзать в любом агенте без установки (агент просто прочитал его как скилл), CLI вызывается без установки в агента — в отличие от MCP. Появился **Playwright CLI** (помимо давнего Playwright MCP), решающий проблему переполнения контекста; в Antigravity тоже есть браузерный агент, но контекст «быстро выжирается». QA для агента в токенах оказался дороже генерации кода.

> [Денис]: MCP не дает никакой дополнительной ценности.

> [Ведущий]: мне кажется уже MCP чуть ли не полудохлой технологией

**Цепочка рассуждения (Денис уточняет, что MCP не стоит на месте):**
1. Изначальное решение декларировать все тулы upfront было неудачным — много тулов нагружают систему.
2. Код-агенты получили специальный тул для поиска/фильтрации тулов и **lazy**-декларацию (грузятся только когда надо).
3. Это повторяет подход скиллов → острота проблемы MCP спала.

**Что это даёт:** для большинства задач Денис целиком перешёл на CLI-инструменты + скиллы.

## 12. Скиллы будущего и оргвопросы (синхронизация Jira/Confluence/Git)

Скиллов «наставляешь пачками», и уже нужен **инструмент поиска релевантного скилла** (по аналогии с поиском тулов в MCP) — его пока нет, но это «следующий логичный шаг». Первый шаг сделал Anthropic: skill-creator теперь умеет улучшать описание скилла, аудировать его и **делать эвал** — запускает систему без скилла и со скиллом, сравнивает и выдаёт не оценочное мнение, а результаты тестирования.

Финальный вопрос (от зрителя Дмитрия): обычно задачи в Jira, документация в Confluence — как синхронизировать с Memory Bank и Git? Денис ведёт это **отдельно**: даёт агентскому куску полную документацию в Memory Bank, а синхронизацию ждёт от индустрии (инструменты будут «не для людей, а для связок людей+агентов»).

**Конкретика:** существует CLI для Confluence (прокси к API). Codalive сейчас добавляет поддержку не только кодовых баз, но и **Confluence**, а клиенты уже загружают выгрузки чатов — из всего получается «универсальный очень хороший **RAG**».

> [Денис]: для агента, еще раз повторяюсь, сильно удобнее писать файлик.

**Что это даёт:** пока инструменты не адаптированы — либо ждать, либо «костылить» синхронизацию; для агента файловый формат остаётся самым удобным.

## Сквозные концепции

### Memory Bank как контекстный движок
Проходит через темы 3–8 и 12: файловая, структурированная база знаний проекта, из которой агент **граундит** хотелку и добирает контекст кусочками. Совмещает роли документации-для-агента, таск-трекера и базы знаний. Управляется индексами с аннотированными ссылками и принципом Single Source of Truth.

### Цикл обратной связи / детерминизм
Темы 6, 9, 10: модель не может умозрительно подтвердить реализацию (ограничение в 1–2 уровня абстракции), поэтому каждую хотелку замыкает детерминированный приёмочный сценарий. Это же объясняет недоверие к «гуляющему» AI-QA и предпочтение N2N-тестов по стабильным идентификаторам.

### Skill + CLI вместо MCP
Темы 7, 11, 12: универсальная связка, не требующая установки в агента; MCP теряет ценность как «толстый» upfront-протокол, но эволюционирует в сторону lazy-загрузки и поиска тулов — тем же путём, что и скиллы.

## Что взять с собой
- Заставляйте агента переформулировать хотелку, заполнять недосказанности и **задавать уточняющие вопросы** до планирования — так вы не опираетесь на галлюцинации.
- Ведите **Memory Bank** файлами; в индексах пишите не только «что», но и «зачем читать» (аннотированные ссылки).
- Держите **Single Source of Truth** по «пирамиде знаний»: код = *как*, документация = *почему/для чего*; не дублируйте сигнатуры.
- На каждую хотелку — **детерминированный приёмочный сценарий** с подготовленным seed; без него фичу «проверить невозможно».
- Описывайте интерфейсы **структурно** со стабильными идентификаторами (`data-testid`) и оборачивайте в Page Object Model — даже для не-браузерных UI.
- Предпочитайте классические **N2N-тесты** «гуляющему» AI-QA ради повторяемости; ошибка, найденная агентом вручную, — это провал тест-системы.
- Нарезайте работу **вертикальными слайсами**: меньше зона изменений → агент лучше продумывает edge-кейсы.
- Переводите MCP в **CLI + Skill** (например, через MCPorter); это универсальнее и не нагружает контекст.
- Реверс-инжинирьте свой готовый проект в **обобщённый скилл** через skill-creator / скилл-ревьюер.

## Глоссарий
- **Memory Bank** — структурированная файловая база знаний проекта для агента (спеки, Epic/Feature, домен, MBB-принципы); источник контекста и граундинга.
- **MBB (Memory Bank Bible)** — папка с принципами ведения Memory Bank, которую агент читает первой.
- **Граундинг (grounding)** — привязка хотелки/фичи к текущему состоянию конкретной системы.
- **Спецификация / Spec-Driven Development** — описание «как система сделана сейчас» (по C4, level 1) как основа планирования; методологий несколько — от одного документа до design/план/спека/таски.
- **Epic / Feature** — нарезка планов вокруг ценности для пользователя; Epic ≈ roadmap со статусом во FrontMatter, Feature — минимальная единица delivery.
- **Single Source of Truth** — каждое сведение хранится только в одном месте; защита от дублирования и дрифта.
- **Пирамида знаний** — код хранит «как», документация — «почему/для чего»; сигнатуры в доку не выносятся.
- **Progressive Disclosure** — добор контекста кусочками по структуре Memory Bank, без выкачивания всего сразу.
- **Приёмочный сценарий** — детерминированный (интеграционный) тест от имени пользователя, подтверждающий реализацию хотелки; требует подготовленный seed.
- **Page Object Model** — обёртка-API над экраном со стабильными идентификаторами (`data-testid`); универсальна за пределами браузеров.
- **Вертикальный слайс** — нарезка по вертикальной функциональности, локализующая зону изменений и упрощающая тестирование.
- **Skill + CLI** — переиспользуемая связка вместо MCP: не требует установки в агента, не нагружает контекст (конвертация через MCPorter).
- **Swarm** — оркестратор-«рой» агентов (у OpenAI); хорош в сборе/поиске, слаб в изменении данных, дорог по токенам.
